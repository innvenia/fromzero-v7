## Conclusión ejecutiva

El avance de Sprints 1 a 8 produjo una base local importante, pero el proceso permitió que capacidades documentadas como bloqueantes quedaran cerradas como "completadas localmente" sin validación real contra Supabase, sin SonarQube activo y con preguntas críticas acumuladas. El problema no es solo técnico: hay fallos de metodología, fallos del procedimiento de transición entre Sprints, fallos documentales y fallos de ejecución/configuración.

Antes de iniciar Sprint 9, el proyecto debe entrar en una fase corta de reconciliación. Sprint 9 no debería comenzar hasta cerrar, diferir formalmente con riesgo aceptado o validar empíricamente los gates de Supabase, SonarQube, secretos/MCP, handlers autenticados, ADRs pendientes, consistencia documental y preguntas ya respondidas.

## Criterio de clasificación

| Tipo | Definición usada |
|---|---|
| Fallo metodológico | La metodología permitió o indujo una decisión, pregunta o avance incorrecto aunque existía información suficiente para bloquearlo o resolverlo antes. |
| Fallo de procedimiento Sprint | La ejecución de un Sprint, su cierre o la transición al siguiente no aplicó correctamente los gates ya definidos. |
| Fallo documental | La documentación del proyecto es incompleta, contradictoria, no está inventariada o no distingue fuente normativa de soporte operativo. |
| Fallo de ejecución/configuración | El proyecto local contradice documentación vigente o deja una condición operativa insegura. |
| Fallo de arquitectura/producto | Una decisión de diseño, contrato, extensibilidad o naming del framework quedó ambigua o endurecida sin cierre explícito. |
| Fallo de gobernanza | Falta trazabilidad de aprobación, estado, baseline Git o separación de cambios. |
| Deuda aceptable | Pendiente explícito, no bloqueante todavía, con dueño, condición y momento de cierre claros. |

## Taxonomía final

La auditoría se debe leer con dos ejes separados:

| Eje | Pregunta que responde | Categorías |
|---|---|---|
| Origen del problema | ¿Dónde nació el error o conflicto? | Metodología, ejecución del Sprint, documentación, configuración/código, arquitectura/producto, gobernanza. |
| Tratamiento requerido | ¿Qué hay que hacer para corregirlo? | Cambiar metodología, corregir artefactos del proyecto, actualizar documentación, implementar/validar, pedir decisión, versionar baseline. |

Clasificación normalizada:

| Código | Categoría | Definición práctica |
|---|---|---|
| M | Metodología | Reglas FromZero, gates, forma de preguntar, Definition of Ready/Done, transición entre Sprints. |
| E | Ejecución en este proyecto | Cómo se aplicó la metodología en Sprints 1 a 8, cierres locales, pruebas, handlers, migraciones. |
| D | Documentación del proyecto | PRD, referencias, inventarios, ADRs, State, Plan, contradicciones o fuentes incompletas. |
| C | Configuración/código | Estado real del repositorio, `.mcp.json`, rutas API, schemas, migraciones, tests. |
| A | Arquitectura/producto | Decisiones de framework, extensibilidad, perfiles, bootstrap, Core AI, APIs y contratos. |
| G | Gobernanza/trazabilidad | Aprobaciones, commits, archivos sin trackear, baseline revisable, separación de cambios. |

## Hallazgos

### H1 - Supabase dev era un gate temprano y quedó como pendiente local

**Clasificación:** fallo metodológico y de procedimiento Sprint.
**Severidad:** alta.

Evidencia:

- `docs/DEPENDENCY_MATRIX.md` declara como fundacional "Supabase local o proyecto dev conectado", migraciones versionadas y `.env.example` completo.
- `docs/REFERENCE_STACK.md` define Supabase como base de datos, Auth, Storage y canal de conexión por MCP/CLI.
- `artifacts/FROMZERO_QUESTIONNAIRE.md` ya había decidido trabajar directamente con proyecto cloud en `supabase.com` y SQL versionado.
- `artifacts/FROMZERO_STATE.md` marca Sprints 3 a 8 como completados localmente, con migraciones no aplicadas contra Supabase local/cloud.
- `artifacts/test-plans/sprint-3.md` y posteriores dejan RLS como validación estática o SQL versionado local.
- El dueño respondió en P11, P12, P27, P34 y P52 que Supabase cloud debió estar activo desde antes de Sprint 1.

Impacto:

- RLS, RBAC, storage, signed URLs, jobs `pg_cron`, imports/exports y handlers no tienen evidencia dinámica suficiente.
- Hay riesgo de que contratos TypeScript o SQL versionado no funcionen al aplicarse realmente.
- El proyecto acumula reproceso al intentar validar ocho Sprints después.

Acción sugerida:

- Pausar Sprint 9.
- Conectar Supabase cloud development como entorno dev de referencia.
- Confirmar `project-ref`, variables locales ignoradas por Git y permisos mínimos.
- Aplicar migraciones de Sprints 3, 4, 6, 7 y 8 en entorno no productivo.
- Ejecutar pruebas dinámicas de RLS cross-tenant, bootstrap, storage, jobs y queries críticas.
- Reabrir estado de Sprints 3 a 8 como `cerrado localmente / pendiente validación Supabase` hasta pasar gates reales.

### H2 - SonarQube fue planificado demasiado tarde para la expectativa del dueño

**Clasificación:** fallo metodológico y de priorización.
**Severidad:** alta.

Evidencia:

- `docs/REFERENCE_STACK.md` incluye SonarQube/SonarCloud como herramienta de calidad, SAST, bugs, vulnerabilidades y coverage.
- `docs/SECURITY_ASSURANCE.md` exige revisión con Sonar dentro del SSDLC y quality gate de CI antes de release.
- `docs/DEPENDENCY_MATRIX.md` lista SonarQube/SonarCloud como hardening bloqueante.
- `artifacts/FROMZERO_PLAN.md` difiere SonarQube a Sprint 11.
- El dueño respondió en P27 y P55 que SonarQube debía estar activo desde el inicio.
- `package.json` no contiene script Sonar ni evidencia de scanner/CI.

Impacto:

- El código de Sprints 1 a 8 no tuvo análisis externo continuo.
- Hallazgos de deuda, bugs, duplicación, seguridad o coverage pueden aparecer tarde y generar reproceso.

Acción sugerida:

- Activar SonarQube en modo informativo antes de Sprint 9.
- Agregar gate bloqueante progresivo: primero baseline, luego umbrales por nuevo código.
- Registrar evidencia de ejecución y quality gate en el estado operativo.
- No esperar a Sprint 11 para descubrir deuda estructural acumulada.

### H3 - El cierre de Sprints permitió "completado localmente" como si fuera suficiente

**Clasificación:** fallo de procedimiento Sprint.
**Severidad:** alta.

Evidencia:

- `artifacts/FROMZERO_STATE.md` usa estados `completado localmente` en Sprints con dependencias de base real, storage, jobs e integraciones.
- `artifacts/FROMZERO_PLAN.md` declara gates de RLS, migraciones, automatización y servicios externos por Sprint, pero también permite avanzar con aprobaciones separadas.
- `artifacts/SPRINT_1_8_DECISION_QUESTIONNAIRE.md` resume Sprints 3 a 8 con limitaciones relevantes sin impedir el avance.

Impacto:

- El lenguaje de cierre oculta la diferencia entre contrato local, código ejecutable y comportamiento integrado.
- El siguiente Sprint hereda deuda no cerrada como si fuera dependencia resuelta.

Acción sugerida:

- Separar estados:
  - `cerrado validado`.
  - `cerrado localmente`.
  - `contrato implementado, integración pendiente`.
  - `bloqueado por gate externo`.
- Prohibir usar `completado` sin calificador cuando el Sprint dependa de Supabase, SonarQube, Storage, provider real, CI o jobs reales.
- Cada cierre debe generar un registro de deuda con dueño, fecha límite y Sprint bloqueado si no se resuelve.

### H4 - Se acumularon preguntas que debieron resolverse por gate

**Clasificación:** fallo metodológico y de procedimiento Sprint.
**Severidad:** alta.

Evidencia:

- El cuestionario Sprint 1-8 contiene 62 preguntas.
- Varias respuestas del dueño indican "no entiendo", "ya está documentado" o "debió pedirse desde el inicio".
- `artifacts/FROMZERO_CONTEXT.md` ya había identificado como crítico cerrar Supabase, migraciones, proveedores, CI, observabilidad, RBAC, API inventory y valores de bootstrap.
- `artifacts/FROMZERO_QUESTIONNAIRE.md` quedó aprobado con 0 preguntas críticas pendientes, pero no impidió que después aparecieran preguntas críticas de ejecución.

Impacto:

- Se mezclaron preguntas de producto, preguntas técnicas, preguntas de activación de servicios y preguntas por falta de explicación.
- El dueño tuvo que reprocesar decisiones que debieron quedar cerradas antes o al cierre de cada Sprint.

Acción sugerida:

- Crear un gate obligatorio `Preguntas críticas del Sprint = 0` antes de iniciar el siguiente Sprint.
- Si una pregunta aparece durante Sprint N, debe cerrarse antes de Sprint N+1 o quedar diferida con:
  - razón;
  - riesgo;
  - dueño;
  - fecha o Sprint de cierre;
  - condición que bloquea.
- Las preguntas que solo piden confirmar algo documentado deben registrarse como "decisión documentada asumida", no presentarse como opción abierta.

### H5 - Algunas preguntas reabrieron decisiones ya documentadas

**Clasificación:** fallo metodológico de lectura y trazabilidad.
**Severidad:** media-alta.

Evidencia:

- CRUD, Grid Universal, Module Factory y Server Actions están ampliamente definidos en `docs/PRD.md`, `docs/REFERENCE_ARCHITECTURE.md` y `docs/REFERENCE_MODULES.md`.
- Payment Gateway, subscriptions, statements, invoices y Stripe como adapter configurable están definidos en PRD, arquitectura, stack y módulos.
- Core AI, `ai_models`, proveedores, tracking de costos y `CORE_AI_SECRET` están definidos en PRD, arquitectura, stack y módulos.
- En el cuestionario Sprint 1-8, el dueño marca varias preguntas como ya documentadas o mal planteadas.

Impacto:

- La metodología genera fricción innecesaria.
- Se diluye la autoridad de `docs/` como fuente de verdad.
- El usuario percibe falta de lectura o pérdida de contexto entre Sprints.

Acción sugerida:

- Antes de preguntar, ejecutar una clasificación:
  - `documentado y no contradictorio`: asumir y citar.
  - `documentado pero contradictorio`: preguntar solo por resolución.
  - `no documentado`: preguntar.
  - `documentado pero requiere orden/profundidad`: preguntar por secuencia, no por alcance.
- En cada pregunta incluir fuente documental y por qué no basta con asumirla.

### H6 - La política de secretos está redactada de forma ambigua

**Clasificación:** fallo metodológico y de comunicación.
**Severidad:** alta.

Evidencia:

- `docs/BOOTSTRAP_REFERENCE.md` permite `.env` y `.env.local` con valores reales fuera de Git y exige `.env.example` versionado con placeholders.
- `docs/SECURITY_ASSURANCE.md` prohíbe secretos reales en frontend, logs, código o docs.
- Varios artefactos usan la frase corta "Sin secretos ni `.env` reales", que el dueño interpretó como prohibición de usar secretos localmente.
- `.env.example` contiene placeholders y variables necesarias.
- `.gitignore` ignora `.env`, `.env.*` y `.mcp.json`.

Impacto:

- Se bloquea o retrasa la activación de servicios necesarios.
- El equipo puede confundir "no versionar ni exponer secretos" con "no usar secretos".

Acción sugerida:

- Reescribir regla operativa como:
  - Permitido: secretos reales en `.env.local`, variables del sistema, CI secrets o vault.
  - Prohibido: secretos en Git, código, docs, logs, chats, screenshots o exports.
  - Obligatorio: `.env.example` con placeholders.
  - Obligatorio: secret scan antes de commit y antes de compartir artefactos.
- No cambiar otros artefactos hasta que el dueño apruebe la reconciliación.

### H7 - `.mcp.json` local contradice la documentación de MCP

**Clasificación:** fallo de ejecución/configuración.
**Severidad:** crítica.

Evidencia:

- `docs/MCP_SETUP.md` dice que `.mcp.json` no contiene secretos inline.
- La verificación sanitizada de `.mcp.json` detectó valores tipo token inline para Supabase y SonarQube.
- `git ls-files -- .mcp.json` no devolvió tracking.
- `git check-ignore -v -- .mcp.json .env .env.local` confirmó que `.mcp.json`, `.env` y `.env.local` están ignorados por `.gitignore`.

Impacto:

- El riesgo de Git está mitigado por `.gitignore`, pero el riesgo operativo existe si esos tokens fueron pegados en chats, logs, respaldos o capturas.
- El documento `docs/MCP_SETUP.md` está desactualizado frente al estado local real.

Acción sugerida:

- Rotar tokens si fueron compartidos fuera del entorno local seguro o pegados previamente en conversación.
- Cambiar `.mcp.json` para leer tokens desde variables externas, no inline.
- Mantener `.mcp.json` ignorado.
- Crear más adelante `.mcp.example.json` sin secretos si se necesita documentación versionable.
- Registrar un gate previo a activar MCP: no token inline, `project-ref` Supabase limitado, herramientas destructivas deshabilitadas salvo aprobación puntual.

### H8 - El modelo de activación de servicios mezcla servicios esenciales y servicios opcionales

**Clasificación:** fallo metodológico.
**Severidad:** alta.

Evidencia:

- El plan trata Supabase, SonarQube, Stripe, Resend, Inngest, OpenRouter, MCP, migraciones y cloud como aprobaciones separadas genéricas.
- La documentación define Supabase como dependencia base, no como integración opcional.
- SonarQube es un gate de calidad esperado por el dueño desde el inicio.
- Stripe, Resend, OpenRouter e Inngest pueden activarse por adapter y con mocks hasta que el Sprint lo requiera.

Impacto:

- Servicios esenciales para validar el framework quedan diferidos como si fueran equivalentes a cobros reales o producción.
- Se acumula deuda de entorno.

Acción sugerida:

- Definir tres niveles:
  - Nivel 1 esencial dev: Supabase dev, SQL versionado, SonarQube informativo, GitHub/CI, secret scan.
  - Nivel 2 integración controlada: Resend sandbox/dev, Stripe test mode, OpenRouter dev, Inngest dev.
  - Nivel 3 alto riesgo: producción, cobros reales, migraciones destructivas, purgas reales, webhooks externos reales.
- Nivel 1 debe estar listo antes de Build o antes del primer Sprint que lo necesite.
- Nivel 3 siempre requiere aprobación puntual.

### H9 - Faltó explicar conceptos técnicos antes de pedir decisión

**Clasificación:** fallo metodológico de comunicación.
**Severidad:** media.

Evidencia:

- El dueño pidió explicación sobre packs, handlers, bootstrap, CI, Inngest, observabilidad, k6, webhooks y purgas reales.
- Las preguntas estaban formuladas para revisión técnica, no para dueño no experto.
- FromZero exige preguntas en lenguaje simple, con impacto y ayuda visible.

Impacto:

- El dueño no puede aprobar con criterio.
- Respuestas válidas quedan bloqueadas por vocabulario.

Acción sugerida:

- Cada pregunta técnica debe incluir:
  - qué significa en lenguaje simple;
  - por qué importa;
  - qué pasa si se elige cada opción;
  - qué riesgo se acepta;
  - recomendación segura;
  - nota técnica separada.
- Términos como CI, k6, handler, Inngest, MCP y bootstrap no deben aparecer sin definición breve.

### H10 - Handlers autenticados y endpoints quedaron como contratos pendientes

**Clasificación:** fallo de procedimiento Sprint.
**Severidad:** media-alta.

Evidencia:

- `docs/API_ENDPOINT_INVENTORY.md` marca handlers CRUD pendientes para Settings, Modules, Plans, Tenants, Users, Profiles, Invitations, API keys y otros dominios.
- `artifacts/SPRINT_1_8_DECISION_QUESTIONNAIRE.md` pregunta en P51 cuándo se implementarán handlers autenticados.
- Sprints 3 a 8 avanzaron con contratos Zod y módulos, pero no cerraron handlers autenticados.

Impacto:

- La API-first prometida queda incompleta.
- Sprint 9 puede construir Core AI sobre una base de endpoints aún incompleta.

Acción sugerida:

- Antes de Sprint 9, decidir si habrá Sprint 8.1 de reconciliación API o si Sprint 9 queda bloqueado hasta implementar handlers mínimos.
- Como mínimo, cerrar handlers de Settings, Modules, Plans, Tenants, Users, Profiles, Invitations y API keys con auth, tenant context, RBAC, rate limit, errores seguros y auditoría.

### H11 - Las revisiones especialistas quedaron como revisión secuencial sin independencia real

**Clasificación:** deuda metodológica.
**Severidad:** media.

Evidencia:

- `artifacts/FROMZERO_PLAN.md` registra arquitectura, seguridad, UI, rendimiento y testing como revisión secuencial, sin subagente real verificado.
- También recomienda agentes futuros para `database` e `integrations`, pero los deja en backlog.

Impacto:

- En Sprints con RLS, webhooks, billing, jobs e IA, la revisión del mismo agente puede no ser suficiente.

Acción sugerida:

- Para limpieza pre-Sprint 9, ejecutar al menos revisiones independientes o checklist adversarial de:
  - base de datos/RLS;
  - seguridad/secrets;
  - integraciones/webhooks/jobs;
  - SonarQube/deuda técnica.
- Si no hay subagentes, documentar revisión secuencial con checklist explícito y hallazgos.

### H12 - El inventario documental no incluye documentos operativos críticos

**Clasificación:** fallo documental y metodológico.
**Severidad:** media-alta.

Evidencia:

- `docs/DOCUMENT_INVENTORY.md` afirma que leyendo únicamente `docs/` se obtiene la visión completa del producto.
- Ese inventario no lista `docs/API_ENDPOINT_INVENTORY.md`.
- Ese inventario no lista `docs/MCP_SETUP.md`.
- Ambos documentos existen dentro de `docs/` y son críticos para esta auditoría: uno expone deuda de handlers, el otro define la postura esperada de MCP y secretos.

Impacto:

- Una revisión guiada por el inventario maestro puede omitir deuda API y riesgos MCP.
- Se reduce la capacidad de detectar contradicciones entre documentación y estado local.

Acción sugerida:

- Actualizar `docs/DOCUMENT_INVENTORY.md` para incluir todos los documentos operativos relevantes.

### Acción 8 - Crear Definition of Ready y Definition of Done por Sprint

- Si hay calidad, Sonar/secret scan/audit según etapa.

## Decisiones que no deben mezclarse

| Decisión | Tratamiento correcto |
|---|---|
| Usar secretos localmente | Permitido si están fuera de Git y no se imprimen. |
| Versionar secretos | Prohibido. |
| Activar Supabase dev | Debe tratarse como esencial para Sprints de datos. |
| Activar Supabase producción | Requiere aprobación puntual. |
| Activar SonarQube baseline | Debe ejecutarse temprano. |
| Bloquear release por Sonar | Gate fuerte antes de release; puede endurecerse progresivamente. |
| Activar Resend dev | Debe definirse temprano si se probarán notificaciones reales. |
| Usar Stripe real | Sandbox/test mode sí; cobros reales no. |
| Usar OpenRouter real | Solo tras budget, redaction, logs y revalidación del modelo. |
| Usar Inngest cloud | Requiere explicación y decisión propia. |
| Cobros reales, purgas reales, migraciones destructivas | Siempre aprobación puntual y backup/rollback. |
| Datos demo | Deben marcarse y borrarse sin tocar datos fundacionales. |
| `allow_multi_tenant_users` | Default `false`; falta decidir si es editable. |
| `Guest` vs `Viewer` | Falta decisión terminológica. |

## Riesgo residual si se inicia Sprint 9 sin limpiar

- Core AI se construirá sobre una base de datos no validada dinámicamente.
- OpenRouter y secrets agregarán riesgo sobre una política de secretos todavía ambigua.
- SonarQube puede descubrir tarde deuda generada en ocho Sprints.
- Handlers autenticados pendientes pueden obligar a reestructurar APIs y auditoría.
- Las respuestas del dueño quedarían en un cuestionario paralelo sin impactar Plan/State.
- El inventario documental seguiría ocultando documentos operativos críticos.
- ADRs pendientes seguirían funcionando como decisiones aprobadas de facto.
- Bootstrap, Tenant Zero, demo data y perfiles seguirían sin salida aprobada.
- Las pruebas seguirían siendo principalmente estáticas o de contrato local.
- Los gates de escalabilidad por módulo seguirían sin evidencia.
- Core AI iniciaría sin API, budget, redaction, logs y provider gate completos.
- No habría baseline Git limpio para separar auditoría, plugin y ejecución.
- Se profundiza la brecha entre "contrato local" y "framework operable".

## Recomendación final

Ejecutar un Sprint de reconciliación antes de Sprint 9. No debe ser un Sprint funcional nuevo; debe ser una limpieza de proceso con alcance cerrado:

- saneamiento MCP/secrets;
- conexión Supabase dev y migraciones;
- SonarQube baseline;
- cierre de preguntas críticas;
- reclasificación de Sprints 3 a 8;
- decisión de handlers fundacionales;
- corrección de inventario documental y ADRs pendientes;
- reconciliación API real contra inventario;
- reconciliación bootstrap/demo/perfiles;
- matriz de servicios externos;
- pruebas empíricas mínimas;
- baseline Git limpio;
- actualización posterior de artefactos FromZero con aprobación explícita.

Sprint 9 debe quedar bloqueado hasta que esa reconciliación tenga evidencia suficiente o el dueño apruebe explícitamente un diferido con riesgos aceptados.
